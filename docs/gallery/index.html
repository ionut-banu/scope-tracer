What each join policy does

Nine pieces of StructuredTaskScope code on JDK 27, and the real scope-tracer report each one produced.

Every section has the code that ran, what to look for in its report, and the report itself. The reports are the files in reports/, generated by running the code under a JFR recording and rendering it, never edited by hand; each section links to its report on its own page.

The snippets use TracedScope, the drop-in wrapper, because it lets each task carry a name. The Java agent gives the same report for plain StructuredTaskScope code (see the README), with tasks labelled by where they were forked instead of by name. In the snippets, work(ms, value) sleeps ms milliseconds and returns value, and fail(ms, exception) sleeps and then throws.

One limit applies to every report here: no event records which joiner a scope was opened with, so a report shows what happened to the tasks, not the policy that made it happen.

fail-fast: one failure cancels the rest

TracedScope.open(name) uses the JDK's default joiner, which cancels the scope at the first failure. Look for the red inventory-check row and the two orange cancelled rows: recommendations and reviews were still running, and end at the same instant as the failure (the report marks them cancelled ← #n, pointing at the task that caused it). profile finished before the failure and stays green.

try (var scope = TracedScope.open("fail-fast")) {
  scope.fork("profile", () -> work(50, "profile"));
  scope.fork(
      "inventory-check",
      () -> fail(200, new IllegalStateException("inventory service unavailable")));
  scope.fork("recommendations", () -> work(2000, "recommendations"));
  scope.fork("reviews", () -> work(2000, "reviews"));
  try {
    scope.join();
  } catch (ExecutionException e) {
    // e.getCause() is the IllegalStateException; the two slow tasks were interrupted
  }
}

The report does not name the join policy: nothing in the recording says which joiner the scope was opened with, so this report looks the same as the failure case of allSuccessfulOrThrow() below.

all-successful: wait for everything, keep the results

Joiner.allSuccessfulOrThrow() waits for every task and returns their results. Nothing fails, so nothing is cancelled. Look for the gold-outlined critical path row: the task that finished last, shipping, is what the scope was waiting for, and the scope's bar ends with it.

try (var scope = TracedScope.open("all-successful", Joiner.<String>allSuccessfulOrThrow())) {
  scope.fork("product", () -> work(150, "product"));
  scope.fork("pricing", () -> work(250, "pricing"));
  scope.fork("shipping", () -> work(400, "shipping"));
  scope.join(); // the results, in the order the tasks were forked
}

Open the full all-successful report

The report shows that the scope waited for the slowest task. It does not show that the results were collected: a recording holds events, not values.

any-successful: the first success wins

Joiner.anySuccessfulOrThrow() returns the first result and cancels the rest. Look at the order of events: mirror-1 fails first and cancels nothing (a failure is not the answer this joiner is waiting for), then mirror-2 succeeds, and only then are mirror-3 and mirror-4 cancelled, ending with the success and not with the failure.

try (var scope = TracedScope.open("any-successful", Joiner.<String>anySuccessfulOrThrow())) {
  scope.fork("mirror-1", () -> fail(200, new ConnectException("mirror-1 refused")));
  scope.fork("mirror-2", () -> work(400, "mirror-2"));
  scope.fork("mirror-3", () -> work(2000, "mirror-3"));
  scope.fork("mirror-4", () -> work(2000, "mirror-4"));
  scope.join(); // the first result; the failure of mirror-1 cancelled nothing
}

Open the full any-successful report

Compare with fail-fast above: there a failure cancels the siblings, here a success does. The report shows who was cancelled and when, not the policy that decided it.

await-all: a failure cancels nothing

Joiner.allUntil(subtask -> false) never asks to cancel, so it is the one policy here where a failure leaves the siblings alone. Look for the red metadata row with no orange row after it: transcript kept running and succeeded, and the scope lasted until the slowest task. Nothing is cancelled because the predicate is false for every subtask, so the joiner never cancels the scope; the failure is just an outcome, reported by the subtask's state.

try (var scope = TracedScope.open("await-all", Joiner.<String>allUntil(subtask -> false))) {
  scope.fork("thumbnail", () -> work(150, "thumbnail"));
  scope.fork("metadata", () -> fail(300, new IllegalStateException("metadata unreadable")));
  scope.fork("transcript", () -> work(600, "transcript"));
  scope.join(); // waits for every task; the predicate never asks to cancel
}

Open the full await-all report

The report shows the scope outliving the failure. It does not show the predicate; the same picture could come from any joiner that never cancels.

custom-joiner: your own rule for when to stop

A Joiner can be anything; this one is a quorum that cancels the scope once 2 of 3 replicas have answered. Look for the two green rows and the single orange one: replica-3 is cancelled at the instant replica-2 completes, because onComplete returned true. JDK 27 requires the joiner to implement timeout() as well.

record Quorum<T>(int needed, List<T> results) implements Joiner<T, List<T>, RuntimeException> {
  Quorum(int needed) {
    this(needed, Collections.synchronizedList(new ArrayList<>()));
  }

  @Override
  public boolean onComplete(Subtask<T> subtask) {
    if (subtask.state() == Subtask.State.SUCCESS) {
      results.add(subtask.get());
    }
    return results.size() >= needed; // true cancels the scope
  }

  @Override
  public List<T> result() {
    return List.copyOf(results);
  }

  @Override
  public List<T> timeout() {
    return List.copyOf(results);
  }
}

try (var scope = TracedScope.open("custom-joiner", new Quorum<String>(2))) {
  scope.fork("replica-1", () -> work(150, "replica-1"));
  scope.fork("replica-2", () -> work(300, "replica-2"));
  scope.fork("replica-3", () -> work(2000, "replica-3"));
  scope.join(); // returns as soon as two replicas answered
}

timeout: the scope runs out of time

withTimeout(450 ms) cancels the scope when the time is up, whatever the tasks are doing. Look for one green row (fast, done before the deadline), two orange rows, and the scope closing a few milliseconds after 450 ms. In the code, join() throws an ExecutionException whose cause is StructuredTaskScope.CancelledByTimeoutException.

try (var scope =
    TracedScope.open(
        "timeout",
        Joiner.<String>awaitAllSuccessfulOrThrow(),
        configuration -> configuration.withTimeout(Duration.ofMillis(450)))) {
  scope.fork("fast", () -> work(150, "fast"));
  scope.fork("slow-1", () -> work(2000, "slow-1"));
  scope.fork("slow-2", () -> work(2000, "slow-2"));
  try {
    scope.join();
  } catch (ExecutionException e) {
    if (!(e.getCause() instanceof StructuredTaskScope.CancelledByTimeoutException)) {
      throw e;
    }
    // the timeout cancelled the scope: "slow-1" and "slow-2" were interrupted
  }
}

Open the full timeout report

The report does not mark the timeout itself (issue #66): the orange rows look like any other cancellation, and it is the scope's length that gives the timeout away.

nested: a scope inside a task inside a scope

A task can open a scope of its own, and the report shows who opened what. Three scopes: request, checkout (opened by the task handle-checkout) and payment (opened by take-payment). Each child is indented under the parent scope, its heading says ↳ task n of <parent>, and the row of the task that opened it carries a ↳ <child> link.

try (var request = TracedScope.open("request")) {
  request.fork(
      "handle-checkout",
      () -> {
        try (var checkout = TracedScope.open("checkout")) {
          checkout.fork(
              "take-payment",
              () -> {
                try (var payment = TracedScope.open("payment")) {
                  payment.fork("fraud-check", () -> work(150, "clear"));
                  payment.fork("card-auth", () -> work(300, "authorised"));
                  payment.join();
                }
                return "paid";
              });
          checkout.fork("reserve-stock", () -> work(150, "reserved"));
          checkout.join();
        }
        return "checked out";
      });
  request.fork("load-session", () -> work(100, "session"));
  request.join();
}

Nothing here fails, so this report says nothing about how a failure travels up through the levels; the order-processing section below does.

ignores-interrupt: a task that does not stop when asked

Cancelling a scope interrupts its tasks; it cannot make them stop. reserve-stock fails at once, price-lookup is interrupted and ends with it, but stubborn swallows the interrupt and works on. Look for the green stubborn row ending long after the red one, and for the scope's bar ending with it: close() waits for every task.

try (var scope = TracedScope.open("ignores-interrupt")) {
  scope.fork("reserve-stock", () -> fail(60, new IllegalStateException("out of stock")));
  scope.fork("price-lookup", () -> work(2000, "price"));
  scope.fork(
      "stubborn",
      () -> {
        long end = System.nanoTime() + 700_000_000L;
        while (System.nanoTime() < end) {
          try {
            Thread.sleep(20);
          } catch (InterruptedException e) {
            // swallowed: the task keeps working although its scope was cancelled
          }
        }
        return "stubborn";
      });
  try {
    scope.join();
  } catch (ExecutionException e) {
    // the failure cancelled the scope at once, but close() below waits for "stubborn"
  }
}

Open the full ignores-interrupt report

The report cannot tell a task that ignored the interrupt from one that was never interrupted. The only sign is the scope outliving its failure.

order-processing: a pipeline, one order declined

The order pipeline from OrderProcessingDemo: five orders, each a fulfilment scope (validation, a nested payment-pipeline scope, a nested inventory-reservation scope) and, if it succeeded, a dispatch scope. Repeated scopes are grouped. One order, ORD-002, is declined by its fraud check: open its section (the page below scrolls to it) to see the failure travel up from fraud-check through payment-pipeline-002 to order-processing-ORD-002, cancel the inventory branch, and skip the dispatch.

private static boolean runFulfillment(Order order) throws InterruptedException {
  try (var scope = TracedScope.open("order-processing-" + order.id())) {
    scope.fork("validate-order", () -> validateOrder(order));
    // each of these two tasks opens a scope of its own
    var payment = scope.fork("payment", () -> runPaymentPipeline(order));
    var inventory = scope.fork("inventory", () -> runInventoryReservation(order));
    scope.join(); // the first task to fail cancels the others
    System.out.printf(
        "[%s] ✓ fulfilled  payment=%s  stock=%s%n", order.id(), payment.get(), inventory.get());
    return true;
  } catch (ExecutionException e) {
    // Unwrap nested ExecutionExceptions to surface the original error message.
    Throwable cause = e.getCause();
    while (cause instanceof ExecutionException && cause.getCause() != null) {
      cause = cause.getCause();
    }
    System.out.printf("[%s] ✗ fulfillment failed: %s%n", order.id(), cause.getMessage());
    return false;
  }
}
